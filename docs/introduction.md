# dt：给 Agent 用的动态表格

dt 是一个本机运行的动态表格。Agent 用 CLI 建表、记数据；人在浏览器里实时看同一份数据，也能直接改。记录之间的父子关系和引用关系会自动长成一张知识图谱，不需要额外搭图数据库。

它要解决的不是「再做一个表格」，而是：**Agent 干完活之后，过程、结果和它们之间的关系，能不能被人看见、被别的 Agent 复用、被查询和分析。**

## 三个常见问题

| 问题 | 通常的现状 | dt 的做法 |
|---|---|---|
| Agent 干完活，结果在哪？ | JSON 文件、终端日志、某个临时目录 | 写进带类型的表，页面实时可见 |
| 多个 Agent 一起干，谁做了什么？ | 翻日志、看 git、靠记忆 | 每条写入都记操作者，变更可追溯 |
| 数据和数据之间有什么关系？ | 只存在于 plan 文件或某个人的脑子里 | 父子 + link 字段自动构成可查询的图谱 |

---

## 能力一：Agent 自己建表，自己记数据

不需要等后端建库建表。Agent 用一份 YAML 描述「我要存什么」，就能建出一个域和若干张表；字段不够就加，子结构需要就加子表。

**适合的场景**

- 任务清单、执行日志、评审结论
- 竞品/资讯/文章的采集结果
- 测试用例与运行结果
- 一个项目一套表，互不干扰

**用起来是什么感觉**

- 表结构是声明式的：写清楚字段和说明，`dt` 对比现状生成变更计划，不会误删已有数据。
- 表可以长出多级子表，例如 任务 → 日志 → 日志附件。
- 字段类型覆盖常见需要：文本、数字、日期、单选/多选、链接、人员、附件、自动编号等。
- 给 Agent 看的说明就写在表结构里：域、表、字段都可以写「这是干什么的」，Agent 下次自己就能看懂。

人的体验是：Agent 在前面建表写字，浏览器里刷新就能看到，不需要导数据。

## 能力二：人机在同一张表上协作

dt 把「Agent 写入」和「人编辑」当成同一种操作：同一份数据、同一套校验、同一份变更历史。

- 页面支持表格视图和看板视图，单元格可以直接改。
- Agent 改完，页面很快高亮那一格，并标出是哪个 Agent 改的。
- 人改完，Agent 下次读到的就是新值。
- 两个人同时改一条记录时，用版本号挡住覆盖，而不是静默丢失。
- 附件直接预览：图片、Markdown、代码、PDF；目录附件按树展开。

**适合的场景**

- Agent 生成初稿，人审阅修改，Agent 再基于修改继续跑
- 关键节点需要人拍板，人直接在表格里改状态
- 运营/测试同学实时盯着 Agent 的产出，发现问题随手标注

## 能力三：不建图数据库，也能快速有知识图谱

这是 dt 比较特别的一点：**记录本身就是节点，父子关系和引用字段就是边**。数据已经在表里，图谱就已经在了，不需要额外导入、同步或写 ETL。

```
记录 A ──父子关系──> 记录 B
记录 A ──引用字段──> 记录 C
操作者 ──修改过──> 记录
```

在页面上打开图谱，可以：

- 看一个域的整体结构，或者只看某张表
- 从一个节点出发，按 1/2/3 跳或「全部」找关联记录
- 查两条记录之间是怎么连起来的
- 看哪些记录孤立、哪些引用悬空、哪些依赖成环
- 按「谁改过」「什么时候改的」筛选
- 拖时间轴回放历史，看这张图是怎么长出来的
- 按住 Alt 把一条记录拖到另一条上，直接建立引用

**它能回答的问题**

| 问题 | 对应能力 |
|---|---|
| 这个任务关联了哪些产出、评审和附件？ | 关联查询 |
| 改这条记录会影响谁？删掉会连带删什么？ | 影响预览 |
| 哪些任务依赖已经完成，现在可以开工？ | 依赖就绪 |
| 这批任务按依赖排，哪几层可以并行？ | 拓扑排序 |
| 哪个 Agent 或哪条记录连接最多、最忙？ | 枢纽统计 |
| 数据里有没有断掉的引用、没人连的孤岛？ | 健康检查 |

图谱和查询结果还能导出成 Mermaid 或 Graphviz，直接贴进设计文档。

**快速建立的典型过程**

1. 建一张任务表，加一个指向自己的 `needs` 引用字段；
2. 插入任务，用 `needs` 连依赖；
3. 打开图谱，依赖关系已经画出来了；
4. 用「就绪/拓扑序」回答「先做什么、哪些能并行」。

不需要先设计图 schema，也不需要把表数据搬到另一个系统。

## 能力四：多 Agent 协同的共享事实

多个 Agent 并行干活时，最大的问题不是算力，而是**各自的信息不互通**：A 的产出在某个临时目录，B 不知道；C 改了状态，D 还在用旧值。

dt 可以充当团队的共享事实层：

- **一个域是一个协作空间**。任务、产出、评审、日志都在里面，人和所有 Agent 查同一份。
- **产物直接挂回记录**。Agent 的产出物通常就是一个文件路径，附件字段直接引用它，不复制、不搬运。
- **谁写的清清楚楚**。每条记录有创建者、最后修改者，每次变更都有操作者和字段级差异。
- **角色可以分工**。dt 本身不做权限模型，但可以用「域 + 操作者约定」划边界：例如编排数据只让协调者写，业务数据让产出它的 Agent 写；写错域会被显式拒绝，不会悄悄串数据。

**适合的场景**

- 一个协调 Agent 拆任务，多个执行 Agent 并行做，再汇总
- 采集 → 评审 → 渲染 这类多阶段流水线
- 多个 Agent 围绕同一批数据做不同视角的处理
- 人作为其中一个角色参与协作

## 能力五：数据变了，可以让事情发生

dt 会记录每一次新增、修改、删除，并带上字段级的前后值。在这个基础上可以设「事件绑定」：

- 某个字段变成某个值 → 发 webhook
- 某条记录新增 → 执行一个本机命令
- 状态变成「完成」→ 自动往日志表写一条记录
- 需要人处理 → 投递到页面上的收件箱

**适合的场景**

- 任务完成自动通知下游系统
- 状态变更触发检查脚本
- Agent 之间用数据变化传递信号
- 人机交接：Agent 把需要确认的事放进收件箱，人处理完再继续

投递有游标、按顺序、失败会退避重试，语义是「至少一次」，接收方可以按投递 ID 去重。

## 能力六：跨任务的分析与复盘

因为所有执行数据都在同一套表里，可以直接回答「跨 Job、跨 Agent、跨时间」的问题，而不是逐个翻文件：

- 最近跑了多少任务，成功、跳过、失败各多少？
- 哪个 Agent 承担最多？平均耗时多少？
- 哪些任务被打回过？原因集中在哪？
- 某次检索最终入选了哪些文章？评审理由是什么？
- 哪些环节经常卡住、哪些并行分片其实没跑满？

这些查询既可以在 CLI 里做，也可以在页面上筛，还可以让 Agent 自己查出来写周报或复盘。

## 实战：TEAMS 多 Agent 团队用 dt 收集执行数据

### 背景

TEAMS 是一个多 Agent 编排框架：用户说一句话目标，协调者把它拆成任务 DAG，按能力把节点并发派给不同的 Agent，worker 完成后写回结构化结果，协调者再解锁下游。

TEAMS 的状态事实源是文件。这对调度本身是可靠的，但人很难回答：最近跑了哪些 Job？哪个 Agent 最忙？一个 Job 的 DAG 长什么样？某次检索最后产出了什么？

于是 TEAMS 把执行过程**镜像**到 dt，dt 负责可观察、可查询、可视化，不参与调度决策。

### 两个域，两种职责

| 域 | 存什么 | 谁写 |
|---|---|---|
| `teams` | Agent 花名册、流程模板、Job、任务 DAG、每次运行记录、打回记录 | 只有协调者 |
| `doc_search` | 一次检索任务、提取的实体、搜索方向、候选文章、评审结论、HTML 产出 | 被授权的业务 Agent |

这样分的好处是：

- 编排数据只有一个写入者，不会出现多个 Agent 并发改同一张任务表；
- 业务数据由真正产出它的 Agent 写，操作者字段真实可信；
- 两类数据互不干扰，人可以分别看「团队怎么干活」和「这次活干出了什么」。

### 跑起来之后，数据长什么样

`teams` 域是一棵执行树：

```
Job（一次目标）
└── 任务（DAG 的一个节点）
    ├── 运行记录（每次派发一条，只追加）
    └── 打回记录（评审打回的原因和证据）
```

以本机一次快照为例：36 个 Agent、14 个流程模板、68 个 Job、588 个任务、286 次运行、11 次打回。

`doc_search` 域是一棵业务树：

```
检索任务
├── 实体（系统、接口、术语）
├── 搜索方向（对应一个并行分片）
│   └── 候选文章
│       ├── 评审结论（分数、入选/剔除/重复、理由）
│       └── HTML 产出（文件路径、自检结论）
```

一次真实检索的结果是：提取 51 个实体、拆成 6 个搜索方向、收集 83 篇候选、评审入选 66 篇，产物目录直接挂成附件。

### 人能看到什么

- **看板**：任务按状态分组，一眼看到哪些在跑、哪些完成、哪些卡住。
- **表格**：每个任务派给了谁、跑了多久、结果摘要、产物路径。
- **事件流**：状态每次变化的 before → after，能追到时间和操作者。
- **图谱**：一个 Job 展开成 DAG，任务依赖和运行记录都在图上；哪个 Agent 改过哪条也看得见。
- **收件箱**：需要人处理的消息集中在一处。

### Agent 能拿它做什么

**1. 自动记录，不用额外写周报**

协调者在流程的关键节点写数据：开跑时记 Job 和全部任务，每次派发记一条运行记录，每次状态变化更新任务，打回时记原因和证据，收尾时更新总耗时和产物目录。数据是流程的副产品，不是事后补的。

**2. 用图谱理解一个 Job**

从一个 Job 出发，能直接展开它的模板、主任务、搜索分片、渲染分片和每次运行；用依赖视角还能看出哪几层是并行的。比如一次检索里 6 个搜索分片同层并行、10 个渲染分片同层并行，最后才汇总。

**3. 用查询做横向分析**

对所有任务做一次状态统计，能看到完成、跳过、失败的真实分布；按 Agent 统计能看到负载；按打回记录能看到质量问题集中在哪里。这类口径跨了几十个 Job，用文件状态很难直接算。

**4. 把业务结果当上下文**

Agent 可以按检索任务一次性带出实体、方向、文章、评审和 HTML，直接生成汇总页或回答「这次调研覆盖了哪些系统、漏了哪些」，不用再去翻目录。

### 这个案例的几条原则

1. **dt 是镜像，不是事实源**。TEAMS 的文件和 `team` 命令才是权威，dt 里写的是结构化输出的副本。
2. **dt 是非必要依赖**。单次写入失败不重试、不阻塞流程；dt 不可用就本次流程不再调用。可观察性不该成为主流程的单点故障。
3. **写入权按角色切分**。协调者写编排域，业务 Agent 写自己的业务域，worker 默认不碰 dt。
4. **附件指向最终产物**。记录「产物在哪」，不是「产物副本」，和 TEAMS 的 artifacts 目录天然对齐。
5. **同一份数据同时服务人和 Agent**。人看图看板，Agent 用同样的数据查询和推理。

## 更多可以套用的场景

| 场景 | 怎么用 |
|---|---|
| **多 Agent 内容生产** | 采集、评审、渲染各阶段写同一棵记录树；产物挂附件；图谱看流水线 |
| **研发任务管理** | 项目一个域，任务/子任务/日志/缺陷；看板 + 依赖图 |
| **调研与知识沉淀** | 一次调研一棵树：主题 → 来源 → 笔记 → 结论；按关系追溯依据 |
| **自动化运维记录** | 告警、处理动作、影响范围写成记录并用 link 关联；事件触发通知 |
| **个人知识库 / Agent 记忆** | 一条记忆一条记录，用链接维护关联；Agent 按描述检索 |
| **测试与评测** | 用例、运行、失败原因、附件日志；按批次和状态统计 |

共同点是：**数据结构会变、需要人机共同维护、记录之间有关系、过程比结果同样重要。**

## 适用边界

dt 是给本机单人 / 单机多 Agent 场景设计的：

- 只监听本机，没有登录鉴权，不要当成多人 SaaS；
- 不做公式和汇总字段，计算交给查询方；
- 域之间隔离，引用和图谱都不跨域；
- 附件只记录路径，不托管文件，文件移动后会提示丢失；
- 不做服务端权限模型，团队分工靠域和操作者约定。

换来的是：一个文件存数据、一条命令启动、Agent 不需要复杂客户端、人和 Agent 看到的状态始终一致。

## 快速开始

```bash
# 安装
git clone <repo> && cd <repo>
(cd web && npm ci && npm run build)
uv tool install .

# 启动（CLI 也会自动拉起）
dt serve        # 打开 http://127.0.0.1:8654
```

Agent 侧安装 Skill：

```bash
cp -r skills/* ~/.claude/skills/
```

| Skill | 用途 |
|---|---|
| `dt-schema` | 设计表和字段 |
| `dt-data` | 增删改查、挂附件、查关联 |
| `dt-event-bind` | 创建事件订阅 |
| `dt-event-consume` | 消费事件流、读收件箱 |
